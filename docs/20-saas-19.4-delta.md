## Methodology correction: the saas branches are not a nested chain

The plan's phase 1 item 3 assumed a linear `19.0 → 19.1 → 19.2 → 19.3 → 19.4` progression. The
repository says otherwise, so the analysis method had to change.

```
git merge-base --is-ancestor origin/19.0      origin/saas-19.1   -> false
git merge-base --is-ancestor origin/saas-19.1 origin/saas-19.2   -> false
git merge-base --is-ancestor origin/saas-19.2 origin/saas-19.3   -> false
git merge-base --is-ancestor origin/saas-19.3 origin/saas-19.4   -> false
```

Each saas branch is an **independent fork**. The common ancestor of `19.0` and `saas-19.4` is
`101027acc286` (2025-09-11 — the 19.0 release cut). **8638 commits exist in `19.0` that are not in
`saas-19.4`**: 19.0 maintenance fixes, plus backports that carry different SHAs on each branch.

Consequences, which rule 22 must state:

- Per-boundary commit counts are meaningless as a size measure. `19.0..saas-19.1` alone is 10564
  commits while `19.0..saas-19.4` is 15257.
- The authoritative delta is a **tree comparison** of each serie against `19.0` over our
  touchpoint surface. Attribution ("which serie introduced this") comes from which serie's tree
  first lacks the thing we use — not from ancestry.
- A fix present in `19.0` is **not** automatically present in `saas-19.4`. When porting, never
  assume a 19.0 bugfix travelled; check the target tree.

### 3. `mail.thread._track_subtype` removed — silent behavior loss (3 modules)

Release-note claim (19.3, the only "Technical" entry in any of the four notes): *"Tracking values
have been removed; the tracking message is now generated on the fly."* **Confirmed in source, and
it is bigger than the note suggests.**

| Serie | `addons/mail/models/mail_tracking_value.py` | `def _track_subtype` in `mail/` |
|---|---|---|
| 19.0 | present | present (`mail_thread.py:633`) |
| saas-19.1 | present | present |
| saas-19.2 | present | present |
| saas-19.3 | **absent** | **absent** |
| saas-19.4 | **absent** | **absent** |

`tracking_value_ids` is also gone from `mail.message`. The replacement is a new
`mail/models/mail_track_mixin.py` (`_name = 'mail.track.mixin'`) plus a redesigned `_track_*`
family on `mail.thread` (`_track_log`, `_track_record`, `_track_execute`,
`_track_log_get_default_body`, `_track_log_get_default_subtype`, …). `_track_subtype(initial_values)`
maps to **`_track_log_get_default_subtype(track_init_values)`** — different name, different
parameter name, same job (returns a `mail.message.subtype`).

`tracking=True` on a field **still works**: `mail.track.mixin._valid_field_parameter` explicitly
allows it, so `odoo_typo_reporter`'s single tracked field is safe.

Our three overrides are the problem, because **an override of a method nobody calls does not
raise** — the custom subtype simply stops being applied:

- `business_appointment/models/business_appointment.py:165` (group `20_16`)
- `cloud_base/models/clouds_client.py:269` (group `20_14`)
- `itlibertas_timesheet/models/timetable_timesheet.py:175` (group `20_7`)

This is the first confirmed member of the **silent-loss** class, and it is exactly what the
program's warning gate and feature tests cannot catch by themselves: no error, no warning, no
failed install. Rule 22 must carry a dedicated "dead override" check — for every custom `def
_<core_hook>` override, assert the hook still exists upstream on the target serie. That check
generalizes beyond `_track_subtype` and should run per group at `Gx.3`.

### 4. Eight dead overrides in nine modules (the silent-loss class, generalized)

`_track_subtype` was not an isolated case. Ran the dead-override check across all of `tools`:
extract every method that calls `super()` (111 distinct names, 333 sites via AST), then test whether
that name is still defined anywhere in `odoo` + `enterprise` at the target pin.

| Dead hook | Modules (group) | saas-19.4 successor |
|---|---|---|
| `_track_subtype` | `business_appointment` (`20_16`), `cloud_base` (`20_14`), `itlibertas_timesheet` (`20_7`) | `_track_log_get_default_subtype(track_init_values)` — note the renamed parameter, and it returns an empty subtype recordset rather than `False` |
| `SELF_READABLE_FIELDS` | `header_clock` (`20_17`), `activities_todo` (`20_12`), `odoo_menu_management` (`20_7`) | delete the override; set **`user_writeable=True`** on the `res.users` field itself (`res_users.py:187` allows the parameter, `:211-247` core usage, `:558-562` the access check) |
| `SELF_WRITEABLE_FIELDS` | same three | same |
| `_to_store_defaults` | `cloud_base` (`20_14`) | `_store_*_fields(self, res: Store.FieldList)` family |
| `_extras_to_store` | `message_edit`, `email_suite` (`20_suite`) | `_store_extra_fields(res, *, format_reply)` |
| `_get_store_message_update_extra_fields` | `message_edit` (`20_suite`) | `_store_message_fields` on `mail.message` — the hook left `mail.thread` entirely |
| `_init_store_data` | `message_edit`, `email_suite` (`20_suite`) | `_store_init_fields` / `_store_init_global_fields` (`mail/models/res_users.py:423,450`) |
| `_inverse_datas` | `cloud_base` (`20_14`) | `_inverse_raw` (see finding 5) |

Scale of the upstream churn behind this: `_to_store_defaults` had **29** definitions in core at 19.0
and **zero** at saas-19.4 — the mail Store API was redesigned wholesale around
`Store.FieldList`. `SELF_READABLE_FIELDS` had 13 core definitions and is now a field parameter.

Only the `SELF_*_FIELDS` conversion is mechanical enough to be a rule-22 before/after, and even then
the override is deleted rather than renamed (ours are `@property` methods). The four Store hooks are
**a redesign, not a rename table**: the old hooks appended to a dict or returned name lists, the new
ones receive a `Store.FieldList` and call `res.attr(...)` / `res.extend([...])`. `20_suite` and
`cloud_base` need real rework, so rule 22 lists them as dead hooks plus a port recipe, never as a
substitution.

**Methodology limit, stated so the check is not over-trusted:** this scan asks whether the *name* is
still defined anywhere in `odoo` + `enterprise`. That is why it is evidence of removal but not proof
of a live override — a surviving name on an unrelated model would hide a dead hook, and a
tools-internal `super()` chain would look dead if its name never existed upstream (25 such names
here, correctly ignored). The checker shipped with rule 22 therefore resolves the hook against the
**inherited model** rather than the whole tree.

### 5. `ir.attachment.datas` removed — writes are silently discarded

| Serie | `datas` field on `ir.attachment` |
|---|---|
| 19.0 | `datas = fields.Binary(compute='_compute_datas', inverse='_inverse_datas')` (`ir_attachment.py:472`) |
| saas-19.4 | **gone**; only `raw` (`_compute_raw` / `_inverse_raw`) and `db_datas` remain (`:498-499`) |

Worse than a removal, `_check_contents` actively swallows it:

```python
if 'datas' in values:
    warnings.warn("Use raw, datas has beeen removed")
    values.pop('datas')  # ignoring
```

A `create`/`write` carrying `datas` therefore succeeds and stores **no content**. Note this is also
a semantic change, not just a rename: `datas` was base64, `raw` is bytes.

Occurrence counts are not a work estimate, and an earlier revision of this doc quoted one as if it
were. A bare `\bdatas\b` grep returns 66 hits in 39 files; `"datas"` as a dict key returns 29 in 16
`.py` files; some of those are local variables. Only real `ir.attachment` create/write sites matter.
Confirmed examples: `cloud_base/controllers/cloud_files.py:84` and `portal_files.py:386` pass
`base64.encodebytes(...)` and would silently store nothing. The checker classifies per site instead
of counting matches.

One piece of good luck: because core calls `warnings.warn`, this specific break **is** catchable by
the program's warning gate — unlike the dead overrides, which emit nothing. That asymmetry is
itself the argument for keeping the static hook check in `Gx.3`.

## What this changes in the plan

- Rule 22 must open with the non-nested-branch fact and the "a 19.0 fix may not exist on the target"
  warning.
- Rule 22 needs a **dead-override check**: for every custom override of a core hook, assert the hook
  still exists upstream. `_track_subtype` proves overrides die silently, which no warning gate or
  install test can catch.
- `20_15` (knowsystem) and `20_6` (product) carry the confirmed breaks; `20_15` is the riskiest
  group in the program and should not be an early slot.
- The checks that found these breaks must ship as a repeatable script, not as ad-hoc scans:
  `ai_rules/tools/check_migrate_v20.py`. They found every break in this document cheaply and will
  keep finding them as 20.0 moves; the release notes found one.
- Groups now known to carry confirmed work before any porting starts: **all 18**. `useState`
  alone is 25 modules; `get_param` is most of the rest. The 2026-09-12 claim that `20_2` and
  `20_c` had “no confirmed finding” was the path-only OWL skip.
- Phase 4's pinned image must run the 34 source-confirmed breaks as an explicit regression set,
  since that is how they graduate from "source-confirmed" to "reproduced". Three already have:
  `ir.access` (`KeyError`), `set_param` (`AttributeError`), `useState` (`TypeError`).
- Counts in these docs must state their counting rule. Two earlier revisions published route,
  `_inherit`, controller-subclass and `datas` figures that could not be reproduced, because the
  scans used regex where `ast`/XML parsing was needed. The checker replaces those scans.
- Every existence check must span `odoo` **and** `enterprise`. The first JS pass searched only
  `odoo`, which would have reported `@web_gantt/*` and `@documents/*` as missing.
