# `20_2` feature contract (pilot)

`Gx.1` of the 19 → 20 port. Reconciles the **live** 19.0 app pages on faotools.com, the
module source, and the docs into one list of claims, each with the check that proves it
still holds on the target serie. A claim with no check is a claim we cannot port safely.

Seeded at `Gx.0` from `tools@19.0` `84e7d1c4840` (branch `20_2`, commit `4340624e5f5`).
`Gx.3` unprefixed the five manifests and dropped the dead `crm` `lead_priority`
inherit. `Gx.4` left Layer-1 demo XML unchanged.

## Coverage reality — read this before trusting `Gx.2`

Only `complementary_contact_data` ships tests, and all three are about one i18n defect:

- `test_parse_legacy_comment_splits_json_prefix`
- `test_ru_read_crashes_on_varchar_then_healer_fixes_it`
- `test_partner_web_read_extras_in_ru_after_healer`

`smart_warnings`, `sticky_notes`, `complementary_employee_data` and
`complementary_lead_data` have **no `tests/` package at all**. So the `Gx.2` baseline
proves "install + upgrade + the three i18n tests", not "the features work". Every other
claim below is a **named manual check** in the `Gx.8` review database, and that is the
pilot's real acceptance evidence. Do not report `Gx.7` green as feature coverage.

## Port-relevant surface

- **JS/OWL**: `smart_warnings` 1 file, `sticky_notes` 3, `complementary_contact_data` 4.
  All in `web.assets_backend`. No `enterprise` dependency, so the pilot runs on the
  community lane only — `demo20`, not `demo20e`.
- **Dependencies**: `mail` (`smart_warnings`), `web` (`sticky_notes`), `web` +
  `hr` + `crm` (the complementary family). `hr` and `crm` make `Gx.6` a three-closure
  matrix, not one install.
- **Demo**: three of the five ship Layer-1 demo XML (Gx.4, unchanged). `smart_warnings`
  and `sticky_notes` have Layer-2 loaders in `odootools_demo` (`_load_demo_smart_warnings`,
  `_load_demo_sticky_notes`) plus complementary Layer-2 extras — **Gx.5 is not a no-op**.
- **Manifests**: Gx.3 unprefixed all five (`1.0.15` / `1.0.11` / `1.0.7` / `1.0.3` / `1.0.3`).
- **Checker**: clean after Gx.3. The CRM `lead_priority` group removal is **not** a
  checker kind (named-group inherit, not `inherit_id`) — fold into rule 22 next.
- **A8**: `res.groups.user_ids` / `implied_by_ids` / `all_implied_by_ids` / `all_user_ids`
  are unchanged on saas-19.4. The existing `@api.depends` stays.

## What would make this group fail acceptance

1. A claim above with neither an automated test nor a walked manual check.
2. A tools `WARNING` in the `Gx.7` test window (4.4a gate) — including A6's degrade path
   if it fires unprovoked.
3. `S4` or `A7` behaving differently on the target: both are access claims, and
   `res.groups` changed shape in 19 (rule 21). A silent access widening here is worse
   than a crash.
